# ARM, i686 and 64-bit (x86_64) support audit (2026-11-10)

A read-only audit of what it would take for Syllable (Pyro) to (a) target **i686** properly instead of i586, (b) run on **ARM**, looking at both AArch64 and ARMv7, and (c) run as a **64-bit x86 (x86_64)** system (section 7, added after Rick asked). Note that i686 is still 32-bit; only x86_64 and AArch64 are 64-bit.

**Source.** `Rick-PyroOS/Syllable` at `ca83ddf` (2026-11-09), cloned from the public GitHub repo because Rick's Mac was offline. `Syllable-Build-System` and `Syllable-Ports` couldn't be reached from this session. Facts about `gcc-common.sh` come from the earlier [Rust/Go/Node audit](rust-go-node-audit-2026-11-09.md), which read it directly.

## 1. Short answer

| | i686 baseline | x86_64 | ARM (AArch64) | ARM (ARMv7) |
|---|---|---|---|---|
| 32 or 64-bit | 32 | **64** | **64** | 32 |
| What it is | Change compiler flags, rebuild everything | Long-mode kernel, 64-bit toolchain and libc, LP64 cleanup; PC drivers mostly come along | A new architecture port: kernel, toolchain, libc, drivers, boot, and the same LP64 cleanup | A new architecture port, still 32-bit |
| Effort, one developer | **About 1 week** | **About 8 to 12 months** to a desktop | **About 12 to 18 months** to a desktop in QEMU, plus 2 to 4 months per real board | About 9 to 14 months |
| Removes the 1.5 GB RAM cap? | No | **Yes** | Yes | No |
| Runs fast on Rick's Mac? | Same as today (emulated) | No, emulated (slightly slower than today) | **Yes, near native** with `-accel hvf` | No. Apple Silicon has no 32-bit ARM mode |
| Recommendation | **Do it now**, with SSE2 | **The cheaper first 64-bit step**; real PCs and UEFI | **Recommended ARM target**; easier after x86_64 | Not recommended |

## 2. What Pyro targets today

- **Triple:** `i586-pc-syllable` everywhere: `cmake/syllable-i586.cmake:11,25` (`CMAKE_SYSTEM_PROCESSOR i586`), `cmake/NativeCompilers.cmake:13,61,73`, `cmake/Ports.cmake:161,186,210,392`, `cmake/SyllablePorts.cmake:11,113,129-130,175,183-194`. The linker emulation is `elf_i386_syllable` (`cmake/Platform/Syllable.cmake:3`).
- **Instruction set:** set only by GCC's built-in default, `--with-arch=i586` (`NativeCompilers.cmake:76`, `docs/gcc-upgrade.md:43`, and `gcc-common.sh:16` in the build system). No CMake file passes `-march`, `-mtune`, `-msse*` or `-mfpmath`. So the system is built **without CMOV, without SSE, with x87 floating point**.
- **Two system compilers:** GCC 4.1.2 is still the **default** (`SYLLABLE_COMPILER 4.1.2` in `syllable-i586.cmake:15`); 9.5.0 is the alternative.
- **Kernel already supports SSE in user space.** `cpuid.c:154-166` sets `CR4.OSFXSR` and `CR4.OSXMMEXCPT` when the CPU has them, `save_i387.c` saves state with `fxsave`, and `fault.c:326` handles SIMD exceptions. So user programs can use SSE/SSE2 today. Only the compiler default holds them back.
- **The appserver already picks MMX at run time** (`ddriver.cpp:306-325`, `ddriver_mmx.cpp`).
- `sb run` uses `qemu-system-i386 -cpu max`, which has CMOV, SSE2 and more, so the default dev setup loses nothing by raising the baseline.

## 3. i686 (and SSE2)

### 3.1 Which baseline

Two sensible choices:

1. **Plain i686** (`-march=i686`): adds CMOV and `FCOMI`, still x87 floats. Drops Pentium, Pentium MMX, AMD K6 and early VIA C3.
2. **i686 + SSE2** (`-march=pentium4` or `-march=i686 -msse2 -mfpmath=sse`, tuned `-mtune=generic`): also gives SSE2 floating point. Drops Pentium II/III, Athlon/Athlon XP and the older VIA/Geode parts as well. Every x86 CPU made since about 2003, and every QEMU `-cpu max`, has it.

**Recommendation: i686 + SSE2.** It is what the language audit needed (Go's default `GO386=sse2`, Rust's `i686` targets, correct IEEE float results for Node/V8 and simdutf), it is what Haiku chose for its non-legacy x86 target, and the hardware it drops is 20+ years old. If keeping Pentium III machines alive matters, pick plain i686 instead; the steps are the same minus 3.2 item 2.

**The i386 ABI does not change.** Calling convention, float return in `st(0)`, struct layout and `long double` all stay the same with SSE2 codegen. Existing binaries keep running, and old and new libraries can be mixed. Only the CPUs that can run the result change.

### 3.2 Steps

1. **Toolchain default.** In `gcc-common.sh` and `NativeCompilers.cmake:76`, change `--with-arch=i586` to `--with-arch=pentium4 --with-tune=generic` (or `--with-arch=i686`), for **both** GCC 9.5.0 and GCC 4.1.2. For 9.5.0 also add `--with-fpmath=sse`. For 4.1.2, if its configure doesn't accept `--with-fpmath`, put `-mfpmath=sse` in its `syllable.h` `CC1_SPEC`. Rebuild the toolchain image.
2. **Keep SSE out of the kernel.** This is the one step with a real bug risk. Once the compiler defaults to SSE2, GCC will vectorise kernel loops into `%xmm` registers. The kernel saves FPU state lazily per thread, so that would silently corrupt user FPU/SSE state. Add `-mno-mmx -mno-sse -mno-sse2 -mfpmath=387` (or `-mgeneral-regs-only` on GCC 7+) to the kernel and every kernel driver target in CMake. Verify with `objdump -d kernel.so drivers/*.so | grep -c xmm` = 0.
3. **Refuse to boot on an older CPU.** In `cpuid.c`, if CPUID lacks CMOV (and SSE2, if chosen), print a clear message and halt, instead of crashing later with an invalid-opcode fault in user space.
4. **glibc.** Rebuild glibc 2.7 configured for `i686`, so it picks `sysdeps/i386/i686` (CMOV-based string routines). Keep `--disable-multi-arch` (no IFUNC, as the loader can't do it). The glibc 2.41 plan is unaffected; it gains the same baseline.
5. **Rebuild and test.** Full rebuild, boot `qemu-system-i386 -cpu max` (should be identical), then `-cpu pentium3` and `-cpu pentium` to check the boot-time refusal from step 3.
6. **Later, optional:** replace the MMX blitters in `ddriver_mmx.cpp` with SSE2 versions and drop the run-time check.

### 3.3 Rename the triple?

Changing `i586-pc-syllable` to `i686-pc-syllable` is cosmetic but touches about 20 references in this repo, every port patch in Syllable-Ports, the toolchain image's `TARGET` variable and the sysroot paths. **Recommendation: keep the name now**, change only `--with-arch`, and rename when the glibc 2.41 sysroot is introduced, since that is already a clean break. Rust and Go target names (`i686-pc-syllable`, `GOARCH=386`) don't depend on the GNU triple.

**Effort:** about 1 week, most of it waiting on rebuilds.

## 4. ARM

### 4.1 AArch64 or ARMv7

**Recommendation: AArch64.**

- **Rick's Mac.** Apple Silicon has no AArch32 support at any level, so an ARMv7 Pyro would run under QEMU's software emulation, exactly as slow as x86 Pyro today. AArch64 Pyro would run with `qemu-system-aarch64 -M virt -accel hvf -cpu host` at near native speed. That alone changes the edit-build-boot loop.
- **Hardware.** Raspberry Pi 3/4/5, Apple, Ampere, every current phone and SBC, and the cloud are AArch64. ARMv7 is shrinking.
- **Upstream support.** GCC (from 4.8), glibc (from 2.17), Rust, Go, Node and WebKit all treat aarch64 as first class. ARMv7 is a lower tier in most of them.
- **The cost.** AArch64 is LP64, so it brings the 64-bit cleanup an x86_64 port would also need (section 4.3). That work is shared: once done, x86_64 becomes much cheaper.

ARMv7 would save the LP64 cleanup (roughly 2 to 3 months) and could even use the existing GCC 4.1.2 and glibc 2.7 (which had ARM EABI support), but it buys nothing on Rick's machine and little on hardware people buy today.

### 4.2 Kernel

The kernel has **no architecture layer.** x86 code lives directly in `system/sys/kernel/kernel/` beside generic code, and x86 types leak into generic code and drivers.

**x86-only files** (about 16,000 lines including the boot stage): `intel.s` (188), `syscall.s` (823), `smp_entry.asm` (172), `descriptors.c` (GDT/IDT/TSS, 461), `fault.c` (467), `pagefault.c` (677), `save_i387.c` (282), `virt86.c` (V86 BIOS calls, 561), `apic.c` (777), `smp.c` (868), `cpuid.c` (213), `irq.c` (PIC, 417), `dma.c` (ISA DMA), `udelay.c`, `vesa_gfx.c`, `kernel/boot/*` (`init.asm` 1,030, `start32.s`, `stage2.c`, `loadelf.c`, `lib.c`), and `inc/{intel.h,io_ports.h,pit_timer.h,mc146818.h,mpc.h,virt86.h,apic.h}`.

**x86 leaking into generic code** (files touched, kernel / drivers):

| Pattern | kernel/kernel | kernel/drivers |
|---|---|---|
| `SysCallRegs_s` (x86 register frame; every IRQ handler takes one) | 16 | 48 |
| `cli`/`sti`/`put_cpu_flags`/`save_flags` | 25 | 13 |
| FPU / i387 | 19 | 0 |
| x86 page-table macros (`PTE_*`, `pgd_t`) | 10 (`areas.c` alone has 131 uses) | — |
| `%gs`/GDT (TLD) | 8 | 0 |
| `eflags` | 11 | 1 |
| V86 / `realint` | 12 | 6 |
| `inb`/`outb` port I/O | 5 | 57 |

**What an AArch64 kernel needs, and how it maps:**

| Area | x86 today | AArch64 | Notes |
|---|---|---|---|
| Boot | GRUB legacy (BIOS) → multiboot (`init.c:831`) | Linux arm64 `Image` header, entered by QEMU `-kernel`, U-Boot or a UEFI stub, with a DTB pointer in `x0` | Start with QEMU `-kernel`; add UEFI (GRUB 2 `arm64-efi` or an EFI stub) for real boards. Ties to the GRUB 2 boot image evaluation (2026-11-10), which found the boot path BIOS-only. |
| Hardware discovery | BIOS memory map, MP tables, ACPI RSDP scan at `0xE0000` | Device tree (libfdt) on QEMU and Pi; ACPI on UEFI servers | The bundled ACPICA is portable, but its OS layer (`osl.c`) has x86 assumptions and known bugs (SMP/ACPI audit A1 to A6). |
| MMU | 2-level 32-bit, `PGDIR_SHIFT 22`, no PAE | 4-level, 4 KB granule, 48-bit VA; TTBR0 user / TTBR1 kernel | `areas.c`, `pagefault.c`, `mman.c`, `swap.c`, `fork.c` need the page-table code behind an interface first. |
| Exceptions, syscalls | IDT, `int $0x80`, `syscall.s` | Vector table at `VBAR_EL1`, `svc #0`, number in `x8` | New `SysCallRegs_s` per arch; generic code must stop reading its fields. |
| Interrupts | 8259 PIC + IO-APIC/LAPIC | GICv2/v3 | `irq.c` becomes the x86 back end of a small IRQ-controller interface. |
| Timers | PIT, TSC, LAPIC timer, CMOS RTC | Arm generic timer (`CNTVCT`, `CNTV_*`); PL031 RTC | |
| SMP bring-up | Real-mode trampoline (`smp_entry.asm`) | PSCI `CPU_ON` | Much simpler than x86. |
| FPU/SIMD | Lazy `fxsave` on `#NM` | Lazy or eager save of V0–V31, FPCR/FPSR, trap via `CPACR_EL1` | |
| Per-thread data (TLD) | `%gs` segment rewritten in the GDT on each switch (`schedule.c:1974`) | `TPIDR_EL0` | Easier than x86 and allows real ELF TLS from day one. |
| Atomics and **memory ordering** | `lock`-prefixed asm in `atomic.h`; **no memory barriers defined anywhere** in `include/syllable` | `__atomic` builtins (LSE or LDXR/STXR) with explicit acquire/release | **Biggest hidden risk.** x86 is strongly ordered, so code that hands data between CPUs or to devices through plain stores works today and will race on ARM. Every spinlock, semaphore, message port, ring buffer and driver descriptor ring needs a review for barriers. |
| DMA | Cache-coherent | Coherent on QEMU `virt`; often **not** on boards | Needs `dma_sync`/cache-maintenance calls in the driver API before real hardware. |
| Port I/O | `inb`/`outb` | Doesn't exist; PCI I/O BARs are MMIO windows | Legacy ISA/PS/2/sound/old-GPU drivers simply don't come along. |
| PCI config | Mechanism #1 (ports `0xCF8`/`0xCFC`) and BIOS | PCIe ECAM from DT or ACPI MCFG | `bus/pci/pci.c` needs a config-space back end interface. |
| ELF loader | `elf.c`: `Elf32_*` only, `R_386_*` only, section headers, `.ctors` | ELF64, `R_AARCH64_{ABS64,RELATIVE,GLOB_DAT,JUMP_SLOT,TLS*}`, program headers, `.init_array` | Overlaps with fixes already wanted for Rust (F7 in the language audit). |
| Signals, ptrace, debugger | x86 `sigcontext`, i387 frames | New `sigcontext`/`ucontext` and ptrace register sets; gdbserver support | |

### 4.3 64-bit (LP64) cleanup

The "Check Syllable 64-bit support" thread found Pyro is 32-bit apart from `off_t`. AArch64 forces the rest:

- **Kernel addresses held in `uint32`.** At least 37 `uint32 n...Addr/Base/Start/End` variables in `kernel/kernel` alone, plus `printk("%08x")` of addresses; `realint`-style `(int)pointer` casts in the boot path.
- **Pointer-to-int casts.** A rough grep finds about 30 in `kernel/kernel`, 119 in `kernel/drivers`, 10 in `kernel/fs`, and a handful in `libsyllable` and the appserver. The real number will come from building with `-Werror=pointer-to-int-cast -Werror=int-to-pointer-cast`.
- **Shared structures.** Anything passed between processes or stored on disk must keep a fixed layout: syscall argument structs, `ioctl` payloads, `os::Message` flattening and appserver protocol structs (both currently assume 4-byte pointers and `long`), and AFS on-disk structs (must stay byte-identical so a disk can move between architectures; AFS is little endian, so byte order is fine).
- **libsyllable/appserver binary-compat stubs** (`vstubs.S`) are tiny `ret` stubs and trivial to port.

### 4.4 Toolchain

- **GCC 4.1.2 can't target AArch64** (support arrived in GCC 4.8), so an ARM port means GCC 9.5 (or later) becomes the only system compiler. Everything built only with 4.1.2 today has to build with 9.5 first. That is worth doing on x86 regardless.
- **GCC 9.5:** add `aarch64-*-syllable*` to `config.gcc`, a `config/aarch64/syllable.h` (start from `aarch64-linux.h` plus the existing i386 `syllable.h` specs), libgcc `t-` files and crt objects. Use DWARF unwinding instead of the `--enable-sjlj-exceptions` used on x86, which needs `dl_iterate_phdr` or `__register_frame_info` from the loader.
- **binutils 2.35:** add an `aarch64elf_syllable` (`elf64-littleaarch64`) emulation, copied from the Linux one with Syllable's linker defaults (SysV hash, entry, `-shared` executables as the specs already force).
- **Ports:** every autotools port needs `config.sub`/`config.guess` to accept `aarch64-*-syllable`. Ports with x86 asm need `--disable-asm` or a generic C path. Webster/WebKit must build with the JIT off at first.

### 4.5 libc

**glibc 2.7 has no AArch64 support** (added in 2.17). So the ARM port depends on the **glibc 2.41 upgrade** already planned in `Syllable/docs/glibc-upgrade.md`. On top of that port, AArch64 needs a `sysdeps/syllable/aarch64` directory: syscall stubs (`svc #0`, `x8`), `setjmp`/`longjmp`, `crt1`/`crti`, `ucontext`, TLS ABI (TCB at `TPIDR_EL0`, variant I), and `bits/` headers. The separate `libpthread` needs its atomics rewritten with `__atomic` builtins and proper barriers.

### 4.6 Appserver and drivers

- **Display:** every appserver video driver relies on PC hardware, and the fallback `vesadrv.cpp` uses V86 BIOS calls (as do `mach64_vesa`, `s3_chrome`, `i855`, `trident`). ARM needs a new driver: **virtio-gpu** (fits QEMU and HVF; also relevant to the SPICE/QXL driver plan (`spice-qxl-driver-plan-2026-11-10.md`)), or `ramfb`/simple-framebuffer for first light. On boards, a UEFI GOP or simple-framebuffer driver, then per-SoC drivers.
- **The tree has no virtio drivers at all.** QEMU `virt` needs virtio-blk (or NVMe), virtio-net, virtio-input (keyboard, mouse/tablet) and virtio-gpu. These are small, well specified drivers and also help x86 under QEMU/KVM.
- **Console:** PL011 UART driver for kernel debug output and gdb.
- **USB:** boards need xHCI (and DWC2/DWC OTG on older Pis); see the USB audit (2026-11-10).
- **Comes along unchanged:** the AFS, ext2, FAT, ISO9660 file systems, the network stack, and most of libsyllable and the apps, once LP64 and barrier issues are fixed.
- **Doesn't come along:** ISA/PS/2/APM/BIOS-disk drivers, the PC sound cards, and the old PC GPU drivers. That's fine.

### 4.7 Build system (`sb`) and images

- Add an `ARCH` setting (`i586` default, `aarch64`) that selects the CMake toolchain file (a new `cmake/syllable-aarch64.cmake`), the toolchain Docker image, the sysroot and the QEMU command.
- QEMU: `qemu-system-aarch64 -M virt,gic-version=3 -cpu host -accel hvf` on Apple Silicon (`-cpu max -accel tcg` elsewhere), `-kernel`, `-device virtio-blk/net/gpu/keyboard/tablet`, `-serial stdio`.
- Image creation (`cmake/Image.cmake`, `cmake/scripts/make-image.sh`) currently reuses GRUB legacy boot sectors from a template disk. ARM needs a GPT image with an EFI system partition, or just the kernel and an AFS root disk for `-kernel` boots.
- gdb: `gdb-multiarch` or `aarch64-elf-gdb` for `sb debug`.
- CMake already isolates the triple in a few variables, so most of the cost is in `Ports.cmake`/`SyllablePorts.cmake`, which hard-code `i586-pc-syllable-*` tool names (about 15 places) and should take them from one variable first.

### 4.9 ARMv7 for comparison

ARMv7 (Cortex-A7/A15, hard-float EABI, VFPv3 + NEON) keeps ILP32, so phase 2 shrinks to a review of barriers and alignment, and GCC 4.1.2 and glibc 2.7 could be used if needed. Its MMU (short-descriptor, 2-level) looks a little like x86's. Its exception model, GIC, generic timer, PSCI, device tree and virtio work are the same size as AArch64's. It saves roughly 3 to 4 months overall, but runs only emulated on Rick's Mac and targets hardware that is going away.

## 5. Decisions for Rick

1. **i686 baseline:** plain i686, or i686 + SSE2 (recommended)? Either is about a week. (x86_64 implies SSE2 anyway.)
2. **ARM:** AArch64 (recommended) or ARMv7.
3. **Which 64-bit port first.** The arch split and the LP64 cleanup are shared between x86_64 and AArch64. **I recommend x86_64 first** (section 7): it's 4 to 6 months cheaper, the existing PC drivers and debugging setup come along, it removes the 1.5 GB cap on real PCs, and it makes UEFI boot possible. AArch64 afterwards reuses about a third of the work. Pick AArch64 first only if running fast on the Mac matters more than all of that.

## 7. 64-bit x86 (x86_64)

Added after Rick asked to evaluate 64-bit. Same source (`ca83ddf`).

### 7.1 Why Pyro is 32-bit today, and what 64-bit fixes

The **1.5 GB RAM cap isn't just a hack, it comes from the memory layout.** `tunables.h:39-45` gives the kernel `0x00100000`–`0x7fffffff` and user programs `0x80000000`–`0xffffffff`. `init_kernel_mem_context()` (`areas.c:3192-3211`) maps *all* physical RAM 1:1 into the kernel's half, so RAM plus kernel areas plus device memory must fit in 2 GB. `init.c:838-843` clips RAM at 1.5 GB to leave room. On 32-bit, fixing that would need PAE plus a Linux-style "highmem" scheme, which the kernel doesn't have. On x86_64 the same "map all RAM" design just works, because the kernel half is 128 TB.

Other wins: 16 general registers instead of 8, SSE2 floats guaranteed, a 47-bit user address space (large files can be `mmap`ed, WebKit and LLVM have room), standard ELF TLS through `%fs`, and the most widely supported target for every toolchain (Rust tier 1, Go `amd64`, Node).

### 7.2 Kernel

What changes, with where it lives today:

| Area | Today (i386) | x86_64 | Size |
|---|---|---|---|
| Boot entry | GRUB legacy multiboot 1 into 32-bit protected mode (`init.c:831`, `kernel/boot/start32.s`) | A small 32-bit stub that builds early page tables, enables PAE and `EFER.LME`, and jumps to 64-bit code. Works from GRUB legacy multiboot 1 or GRUB 2 multiboot 2, so the boot disk can stay as it is at first | Small |
| Memory layout | Kernel low 2 GB, user high 2 GB, all RAM identity-mapped | Usual split: user in the low half, kernel in the top half with a direct map of all RAM and the kernel image at `-2 GB` (`-mcmodel=kernel`). The ELF loader already relocates every image, so moving user space is mostly `tunables.h`, `sysbase.h:76-77` and the area allocator | Medium |
| Page tables | 2-level, `PGDIR_SHIFT 22`, `pgd_t`/`pte_t` macros, 131 uses in `areas.c`, 38 in `pagefault.c` | 4-level (PML4), NX bit. Best done behind the same page-table interface the ARM port needs | Large |
| Descriptors | GDT/IDT/TSS in `descriptors.c`, 8,192-entry GDT in `sysbase.h:61` | 64-bit GDT (16-byte TSS descriptor), 16-byte IDT gates, IST stacks for double fault and NMI | Medium |
| Entry, IRQ, syscalls | `intel.s`, `syscall.s` (823 lines), `int $0x80`, `SysCallRegs_s` | Rewrite in 64-bit asm. Start with `int $0x80` (works in long mode) and move to `syscall`/`sysret` later. New 64-bit `SysCallRegs_s` | Large |
| Per-thread data (TLD) | `%gs` segment with base and limit rewritten in the GDT on each switch (`schedule.c:1974`, `smp.c:861`) | Segment limits don't exist in long mode. Set the `%gs` base through `MSR_GS_BASE` (or `wrgsbase`), and give user TLS its own `%fs` base so standard x86_64 ELF TLS works. The kernel uses `swapgs` for its per-CPU data | Medium |
| V86 BIOS calls | `virt86.c` (561 lines) and `realint` | **V86 mode doesn't exist in long mode.** See 7.4 | Large |
| SMP | Real-mode trampoline `smp_entry.asm` (and the S1 layout bug from the SMP audit) | Trampoline goes real → protected → long mode | Small |
| FPU | Lazy `fxsave`, already in place | Same, plus `-mno-red-zone -mno-sse -mno-mmx` for the kernel | Small |
| ELF loader | `elf.c`, `Elf32_*` and `R_386_*` only | ELF64 and `R_X86_64_{64,PC32,GLOB_DAT,JUMP_SLOT,RELATIVE,TPOFF64,...}`. Kernel modules need PIC or `-mcmodel=kernel` relocations | Medium |
| Signals, ptrace | 32-bit `sigcontext`, i387 frames (`psignals.c`, `save_i387.c`, `ptrace.c`) | 64-bit frames; `fxsave` layout already used | Medium |
| Atomics | `lock cmpxchgl` etc. in `atomic.h` | `q`-suffixed versions, or GCC `__atomic` builtins (which ARM needs too). x86_64 is still strongly ordered, so the barrier problem from 4.2 doesn't bite here | Small |

### 7.3 LP64 cleanup

The same work as section 4.3. Measured on this tree:

- `kernel/kernel`: 514 uses of `uint32` against 115 of `uintptr_t`, at least 37 `uint32` variables named as addresses, 13 files with hard-coded `0x80000000`/`0xffffffff`.
- `kernel/drivers`: 1,321 uses of `uint32` against 14 of `uintptr_t`, and about 119 pointer-to-int casts by grep. Most of those `uint32`s are correct (registers), so the real list comes from compiling with `-Werror=pointer-to-int-cast -Werror=int-to-pointer-cast`.
- `libsyllable` and the appserver look fairly clean (under 20 suspicious casts). The appserver protocol (`protocol.h`) uses fixed-width fields. Structs holding pointers (for example `AR_DeleteWindow_s`) are fine as long as the appserver and all apps are 64-bit together, which they would be.
- AFS on-disk structures must stay exactly the same so disks remain readable by both builds and by `linux-afs`.

### 7.4 BIOS calls (the biggest x86_64-specific problem)

Today these use V86 BIOS calls through `realint`, which can't run in long mode:

| User | File | Replacement |
|---|---|---|
| VESA mode setting (the fallback display driver, plus `mach64_vesa`, `s3_chrome`, `i855`, `trident`) | `appserver/server/vesadrv.cpp` | Take a linear framebuffer from the bootloader (GRUB 2 `gfxpayload` or UEFI GOP) for the default driver. For mode switching, run the VBE BIOS through a real-mode **x86 emulator** (x86emu, which X.org and Haiku use, MIT licensed) |
| PCI BIOS fallback | `bus/pci/pci.c`, `bus/acpi/simple_pci.c` | Drop it; config mechanism #1 (`0xCF8`) and ECAM cover everything x86_64 |
| BIOS disk driver | `disk/bios/bdd.c` (9 calls) | Drop it; ATA, AHCI and USB storage remain. (AHCI, NVMe and virtio-blk are worth adding regardless) |
| APM | `misc/apm` | Drop it; ACPI only |
| PS/2 setup | `ps2/ps2.c`, `ps2aux.c` (1 call each) | Replace the BIOS query with direct controller probing |

### 7.5 Toolchain and libc

- **Triple:** `x86_64-pc-syllable`. GCC 9.5: add it to `config.gcc` with an `i386/syllable64.h` (or a shared `syllable.h` with `TARGET_64BIT` cases, like `linux64.h`), libgcc `t-` files, crt objects; drop SJLJ exceptions for DWARF unwinding. binutils 2.35: an `elf_x86_64_syllable` emulation. GCC 4.1.2 could target x86_64 but there's no reason to; 9.5 becomes the system compiler.
- **Multilib or not:** a 32-bit compatibility layer that runs existing i586 binaries on the 64-bit kernel (like Linux's compat syscalls) would need every syscall struct translated. **Recommendation: no compat layer.** Rebuild everything from source, which the CMake build already does, and keep the i586 build as its own release while it's useful.
- **libc:** unlike AArch64, **glibc 2.7 does support x86_64**, so a 64-bit port could reuse the existing 2.7 port with a new `sysdeps/unix/sysv/syllable/x86_64` next to `i386` (today that holds 13 files: `syscall.S`, `sysdep.S`/`sysdep.h`, `brk.c`, `fork.c`, `atomicity.h`, `sigcontextinfo.h` and a few more). That lets 64-bit work start before the 2.41 upgrade lands. If 2.41 is close, do it there instead, once.
- **Ports:** `config.sub` accepting `x86_64-*-syllable`, `--disable-asm` where a port has only i386 asm, and the usual 64-bit fixes upstream code already has for Linux.

### 7.6 Drivers and appserver

- Most PCI drivers (network, sound, USB host, ATA) come along after the LP64 fixes, because the hardware is the same.
- **DMA limits.** With more than 4 GB of RAM, devices that only do 32-bit DMA (many older NICs, UHCI/OHCI, ATA busmaster, HDA on some chipsets) need memory from below 4 GB. Add a `MEMF_DMA32` allocation zone (and keep the existing ISA `<16 MB` handling). Without it, drivers corrupt memory as soon as a machine has more than 4 GB.
- `vmware` and the planned SPICE/QXL and virtio-gpu drivers are the useful display drivers going forward; the old PC GPU drivers can be built if they compile, or left out.
- `sb`: `qemu-system-x86_64 -cpu max` (the rename the 64-bit thread already scoped), plus an OVMF/UEFI option once the kernel can boot from UEFI.

### 7.8 How x86_64 and AArch64 relate

Phases 1 and 2 (arch split and LP64, about 3 to 5 months) are identical for both ports, and phase 8 (user space) mostly is. So doing x86_64 first makes AArch64 cost roughly 8 to 12 months more instead of 12 to 18. AArch64 adds what x86_64 doesn't need: memory barriers everywhere, GIC/timer/PSCI, device tree, virtio drivers, and glibc 2.41 as a hard requirement.
