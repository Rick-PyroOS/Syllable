# USB subsystem audit (2026-11-10)

This is a read-only audit of the Syllable (Pyro) USB stack, kernel and userspace, looking for memory bugs and correctness problems. It also covers where libusb is used and how to upgrade it. The source was `Rick-PyroOS/Syllable` at `ca83ddf` (2026-11-09), taken from the public GitHub repo because Rick's Mac was offline.

**Files covered** (all paths are under `system/sys/` unless they start with `system/apps`)

- Bus manager: `kernel/drivers/bus/usb/usb.c`, `usb_hub.c`, `libusb.c`, `include/syllable/kernel/usb.h`, `include/syllable/syllable/libusb.h`
- Host controllers: `kernel/drivers/hcd/usb_uhci/usb-uhci.c`, `usb_ohci/usb-ohci.c`, `usb_ehci/hcd.c`, `ehci-q.c`, `ehci-sched.c`. These were reviewed at the unlink, completion and DMA paths, not line by line.
- Class drivers: `kernel/drivers/input/usb_hid/hid.c` + `hid.h`, `kernel/drivers/disk/usb/usb_disk.c` + `transport.c`, `kernel/drivers/misc/usb_printer/usbprinter.c`, plus the shared SCSI read/write path in `kernel/drivers/bus/scsi/scsi_generic.c` that USB disks go through
- Userspace: `appserver/appserver/drivers/input/usbkeyboard/keyboard.cpp`, `usbmouse/usbmouse.cpp`, and the libusb 0.1.12 Syllable backend `system/apps/utils/Builder/packages/Syllable/libusb-0.1.12/patches/syllable.c`

**Not built, so not audited:** `hcd/usb_uhci_old` (not in `hcd/Makefile` SUBDIRS) and `input/usb_mouse` (not in `input/Makefile`). Both could be deleted. Note that the CMake build only builds the bus manager and `usb_disk`. The HCDs, HID and printer drivers come only from the old Makefiles (`docs/cmake-full-status` covers this).

Severity: **Critical** means kernel memory corruption that a common device or an ordinary user action can trigger. **High** means memory corruption, a use-after-free, or a kernel hang on a realistic path, including from a malicious or broken USB device. **Medium** means wrong behaviour, a leak, a narrow race, or a security gap that needs device access. **Low** means cleanup or hardening.

A theme throughout: this is a 2003 port of Linux 2.4 USB that trusts every descriptor the device sends. Any "malicious device" finding is reachable by plugging in a cheap programmable board (a Teensy or a Facedancer, for example). Treat those as real if Pyro is ever used where untrusted people can plug things in.

## 1. Summary of the most important findings

| # | Sev | Where | Problem |
|---|-----|-------|---------|
| K1 | Critical | `libusb.c:127-140` | The userspace I/O ioctl never cancels or frees its URB. After a timeout it frees the DMA buffer while the controller is still writing into it, and every request leaks a packet. |
| K2 | High | `libusb.c:107-123` | The endpoint number from userspace goes unmasked into the pipe word (it can set the pipe type) and into an array index (`psEndpoint[nEPNum]`), so a user gets a kernel out-of-bounds read and can forge an ISO pipe. |
| K3 | High | `libusb.c:134-135` | Reads copy the whole requested size back to userspace, not the actual length, which leaks uninitialised kernel heap. Transfer errors are also reported as success. |
| K4 | High | `libusb.c:348-363`, `usb.c:1154` | On unplug the libusb node, its semaphores and the device are freed while a user thread can still be blocked inside the ioctl. Use-after-free. |
| U1 | High | `usb.c:719-720` | `usb_submit_packet_blocked` frees the packet and *then* reads `psPacket->hWait`. Use-after-free on every submit failure. |
| U2 | High | `usb.c:81-107`, `120-141`, `200-223` | Driver register/deregister hold the `g_hUSBLock` **spinlock** while probing devices. That probe does control transfers, SCSI scans and semaphore waits. Deregister also deletes the driver's semaphore and then locks it. |
| U3 | High | `usb.c:866,949` | `while( nSize >= sizeof(...) )` compares a signed `int` with `size_t`. Once a bad descriptor drives `nSize` negative, the loop walks off the heap buffer. |
| U4 | High | `usb.c:1556-1583` | `wTotalLength` from the device isn't checked against the 9-byte config header, so `usb_parse_config` reads past a short buffer. |
| H1 | High | `usb_hub.c:321,386-387,781,814` | The hub port count (up to 255) isn't clamped to the 16-entry arrays. A hub with more than 16 ports overflows the `portstr[17]` stack buffer and writes past `psChildren[16]` into the device struct. |
| H2 | High | `usb_hub.c:506-525` | The hub is linked into the global list *before* configuration. On failure it is freed but stays linked, so the hub thread then uses freed memory. |
| H3 | High | `usb_hub.c:535-563` | `usb_hub_remove` takes a semaphore and calls `usb_cancel_packet` (which sleeps on UHCI and OHCI) while holding a spinlock with interrupts disabled. |
| O1 | High | `usb-ohci.c:803-818` | After a synchronous unlink, the OHCI code reads and writes `urb_priv->wait` after the interrupt path has already freed `urb_priv`. Every synchronous cancel on OHCI is a use-after-free. |
| D1 | Critical | `hid.c:590,623,689,700-701` | The HID report descriptor parser has no bounds at all. A device-chosen report ID indexes `asReport[256]`, field count overruns `apsField[64]`, and usage ranges overrun a 1024-entry **stack** array. |
| D2 | High | `hid.c:313-323,366-422` | In the interrupt handler: a VLA sized by the device's report count lives on the kernel stack, the `anUsage[]` and keymap indices are unchecked, and `nUsage >= 0 && nUsage >= 255` is always true. |
| D3 | Medium | `hid.c:824` + `hid.h:182` | The HID interrupt URB is up to 32 bytes, but its buffer `anData` is 8 bytes. Any device with a maxpacket over 8 overwrites `zName`. |
| M1 | High | `usb_disk.c:398-405` | Unplugging a USB disk frees nothing and cancels nothing. The interrupt URB stays live, `pusb_dev` is never cleared, and in-flight SCSI commands use the freed device. |
| M2 | High | `scsi_generic.c:103-104,152,234-253,293-337,439-471` | Chunks of `0xffff` bytes aren't sector multiples. Any read or write over 64 KB lands 511 bytes off, which **silently corrupts disk data**. (This is in the SCSI layer; USB disks are its main user.) |
| M3 | Medium-High | `transport.c:391,435`, `transport.c:828` | Mass-storage transfers wait forever, with no timeout. A NAKing device hangs the caller, and CBI can lose its wakeup. |
| P1 | Medium | `usbprinter.c:739-742` | Off-by-one: a 128-byte DESCRIPTION writes `zName[128]`, which is the low byte of `psDev`. |
| L1 | High | userspace libusb 0.1.12 | The libusb is from 2006, with a backend that converts ms to µs with `*100` (timeouts are 10× too short) and returns the requested size instead of the actual size. Section 7 has the upgrade plan. |

## 2. Kernel libusb node (`bus/usb/libusb.c`)

This is the user-to-kernel boundary, so it comes first. Each interface of every device gets `/dev/usb/<bus>/<dev>-<if>` (`libusb.c:319`). Any process that can open the node can drive the device, and ioctls run as the kernel.

### K1. Critical: the I/O path leaks its URB and frees a live DMA buffer

`do_io_request()` (`libusb.c:77-141`):

```c
nError = usb_submit_packet( psPacket );
if( nError == EOK )
    nError = lock_semaphore( psUSBNode->hWait, SEM_NOSIG, psReq->nTimeout );
...
err_free:
    kfree( pData );
```

- `psPacket` is never freed, so **every** bulk or interrupt ioctl leaks one packet.
- On timeout the URB is never cancelled. `pData` is freed while the host controller still owns it, so the controller later DMAs into whatever kmalloc hands out next. When the transfer finally completes, `do_io_complete()` does `UNLOCK(hWait)`, leaving a stale count. The *next* request then returns immediately with a buffer that hasn't been filled.
- Interrupt endpoints in this stack auto-resubmit (`usb-uhci.c:2507-2528`). An interrupt read keeps the URB running forever after the ioctl returns, writing into freed `pData` at the endpoint's interval.

**Fix:** after the wait, check whether it timed out. If so, `usb_cancel_packet()` (synchronously) and only then free. Always `usb_free_packet()`. Submit interrupt URBs with `nInterval` set but one-shot (or cancel after the first completion). Return `psPacket->nStatus` and `nActualLength`.

### K2. High: the endpoint value from userspace isn't validated

- `usb_rcvbulkpipe( dev, psReq->nEndpoint )` shifts the raw `int` left by 15 (`usb.h:301`). Bits 15–16 of the user value land in pipe-type bits 30–31, so a user can turn a "bulk" request into an ISO pipe on a packet allocated with zero ISO frames. The HCD's ISO path then indexes `sISOFrame[]` past the allocation.
- For interrupt requests, `nEPNum = psReq->nEndpoint & USB_PIPE_DEVEP_MASK` (`0x0007ff00`, a *pipe* mask, not an endpoint mask) indexes `psSetting[0].psEndpoint[nEPNum]` (`libusb.c:116-117`). That is an out-of-bounds kernel read, chosen by the user, and a NULL dereference for interfaces with no endpoints. It also always uses alt setting 0.
- Nothing checks that the endpoint belongs to the node's interface, or that a kernel driver (HID, disk) hasn't already claimed it.

**Fix:** `ep = nEndpoint & 0x8f`. Look it up in the *active* alt setting of `psUSBNode->nInterfaceNum`, refuse if it isn't there or if its type doesn't match the ioctl, and refuse if `psIF->psDriver != NULL`. Build the pipe from the descriptor, not from the user value.

### K3. High: kernel heap leaks to userspace on short reads

`memcpy_to_user( psReq->pData, pData, nSize )` (`libusb.c:135`) copies the full requested size. `pData` is `kmalloc` without `MEMF_CLEAR`, so a short read returns stale kernel heap. The ioctl returns `EOK` even when `psPacket->nStatus` is an error, because the status is never read.

**Fix:** clear the buffer or copy only `nActualLength`. Return the length (add an `nActual` out-field to `struct usb_io_request`) and map `nStatus` to an errno.

### K4. High: unplug while a node is open is a use-after-free

`libusb_remove()` (`libusb.c:348-363`) deletes the node, deletes `hLock`, `hWait` and `hOpen`, and frees the node, with no regard for an ioctl in progress. `usb_disconnect()` then frees `psDev`. A thread blocked in `lock_semaphore(hWait)` wakes on a deleted semaphore and dereferences a freed `psUSBNode` and `psDevice`.

**Fix:** reference-count the node. Open takes a reference, and remove marks it dead, cancels its URB, and drops the creator's reference. Free on the last put. Ioctls on a dead node return `-ENODEV`.

### K5. Medium: other libusb.c problems

- `IOCNR_SET_CONFIGURATION` (`:211-222`) swaps `psActConfig` underneath kernel drivers bound to the old config's interfaces (they never get `RemoveDevice`). The libusb nodes made for the old interfaces leak, because `libusb_remove` walks the *new* config. Either refuse when any interface has a kernel driver, or do a full unbind, rebind and node recreation.
- `IOCNR_DO_REQUEST` lets a user send raw `SET_ADDRESS`/`SET_CONFIGURATION`/`SET_INTERFACE`, which desyncs kernel state. Filter standard requests that change state, and route them through the proper calls. `kmalloc(sReq.nSize, MEMF_KERNEL)` (`:182`) isn't NULL-checked.
- `IOCNR_CLEAR_HALT` (`:269-274`) builds a **control pipe on endpoint 0** from the user's endpoint, so `usb_clear_halt()` always clears ep0. libusb's `usb_clear_halt()` has never worked. Use `usb_rcvbulkpipe/usb_sndbulkpipe(dev, ep & 0x0f)` according to `ep & 0x80`.
- `alloc_usb_node()` (`:303-320`) logs on OOM and then dereferences the NULL `psUSBNode`.
- The return values of `memcpy_from_user`/`memcpy_to_user` are ignored everywhere. Errors are a mix of positive (`EAGAIN`, `ENOMEM`, `ENOSYS`) and negative values. Pick the kernel convention (negative) and check every copy.
- The node permissions are whatever `create_device_node` defaults to. Decide whether `/dev/usb/*` should be root- or group-only.

## 3. Bus manager core (`bus/usb/usb.c`)

### U1. High: use-after-free when a blocking submit fails

```c
nStatus = usb_submit_packet( psPacket );
if( nStatus != 0 ) {
    usb_free_packet( psPacket );
    delete_semaphore( psPacket->hWait );   // reads freed memory
```

`usb.c:715-721`. Swap the two lines.

Also in `usb_submit_packet_blocked`:
- The semaphore is deleted (`:731`) *before* the timeout cancel (`:741`). On UHCI the cancel runs the completion synchronously, which calls `UNLOCK()` on the deleted ID. If semaphore IDs are reused, that releases somebody else's semaphore. Cancel first, then delete.
- `lock_semaphore(..., nTimeOut)` is retried with the full timeout each time round the loop, not the remaining time. That's harmless but wrong.
- `usb_internal_control_msg` (`:766`) collapses every error to `-1`, which hides `-EPIPE`/`-ETIMEDOUT` from callers that check for them (`usb_get_descriptor:1212` retries on `-EPIPE` but never sees it).

### U2. High: sleeping under the `g_hUSBLock` spinlock, plus a deregister use-after-free

`usb_register_driver` (`:81-107`) and `usb_register_driver_force` (`:123-141`) hold `spinlock(&g_hUSBLock)` across `usb_find_driver()`. That calls `LOCK(psDev->hLock)`, `LOCK(psDriver->hLock)` and the driver's `AddDevice`, which for `usb_disk` means string fetches, GET_MAX_LUN and a full SCSI bus scan. With the per-CPU recursion check described in finding L1 of the SMP/ACPI audit, a second thread on the same CPU walks straight into the "locked" list. Every HID, disk and printer driver registers this way through `add_driver_resistant`.

`usb_deregister_driver` (`:194-225`):
- reads `g_psFirstUSBDriver` *before* taking the lock (`:199` vs `:200`)
- `delete_semaphore( psNextDriver->hLock )` at `:206`, then `usb_remove_driver()` does `LOCK( psDriver->hLock )` on the deleted semaphore (`:174`)
- calls `RemoveDevice` (which sleeps) under the spinlock

Also: the failure path of `usb_register_driver` leaks `hLock`. `usb_find_interface_driver` (`:343-374`) walks the driver list with no lock and publishes `psIF->psDriver` *after* releasing `psDev->hLock` (`:364-366`).

**Fix:** make `g_hUSBLock` a mutex semaphore (`create_semaphore(..., 1, 0)`), or take a snapshot of the bus list under the spinlock and probe outside it. In deregister, delete the driver semaphore last. Set `psIF->psDriver` before unlocking.

### U3. High: signed/unsigned loop bound in the descriptor parsers

`usb_parse_endpoint` (`:866`) and `usb_parse_interface` (`:949`) use `while( nSize >= sizeof( USB_desc_header_s ) )` with `int nSize`. The comparison is unsigned. Neither inner loop checks `psHeader->nLength > nSize` (only `usb_parse_config:1074` does), so a vendor descriptor whose length runs past the end drives `nSize` negative. The loop then keeps going (because `(size_t)-5` is huge) and walks off the end of `pBigbuffer`.

Related problems in the same parsers:
- `memcpy( psEndpoint, pBuffer, USB_DT_ENDPOINT_SIZE )` (`:853-856`) and `memcpy( psIFDesc, pBuffer, USB_DT_INTERFACE_SIZE )` (`:940`) don't check `bLength >= 7/9` or `nSize >= 7/9`.
- `bLength == 0` on an endpoint returns `nParsed = 0` without an error, so the caller fills every remaining endpoint with the same bytes.
- `kmalloc(sizeof(endpoint) * 0)` for `bNumEndpoints == 0` (`:1002`) can return NULL and fail an otherwise valid interface.
- Every error path leaks the allocations made so far.

**Fix:** make `nSize` checks signed (`(int)sizeof(...)`), check `nLength` against `nSize` and against the minimum size in every loop, and skip the endpoint allocation when the count is zero.

### U4. High: config `wTotalLength` is trusted

`usb_get_configuration` (`:1556-1583`) allocates `nTotalLength` bytes. A device can report `wTotalLength` of 0–8, and `usb_parse_config` then `memcpy`s 9 bytes from the short buffer (`:1039`) and starts with a negative `nSize`. Also: `bNumInterfaces` of 0 leads to `kmalloc(0)`, and `bMaxPacketSize0` is accepted as anything, including 0 (`:1728`). The HCDs divide by maxpacket when splitting TDs. Linux requires 8/16/32/64 (and 512 for SuperSpeed).

**Fix:** require `nTotalLength >= USB_DT_CONFIG_SIZE`, `psConfig->nLength >= 9 && <= nTotalLength`, and `bMaxPacketSize0 ∈ {8,16,32,64}`.

### U5. Medium: device lifetime and leaks

- `usb_free_device` (`:621-632`) never frees `psConfig[]`, the interfaces, the endpoints, their `pExtra`, or `pRawDescs[]`, and never deletes `hLock`. Every unplug and every failed enumeration leaks all of these. It also only does `atomic_dec` on the bus refcount, so the bus is never freed.
- `usb_alloc_device`, `usb_alloc_bus` and `usb_alloc_packet` (`:598,238,646`) `memset` the result of a `MEMF_NOBLOCK` kmalloc without a NULL check. `usb_alloc_packet( nISOPackets )` doesn't check for negative or overflowing counts.
- `usb_connect` (`:1182`) searches from address 0. If all 127 are in use it leaves `nDeviceNum == 0`, and the failure path in `usb_new_device` then clears `bDevMap[0]`, which is the root hub's slot.
- `usb_new_device` passes `256` as the size of `zTemp[255]` (`:1692,1771`). It can't currently overflow (strings are at most 126 chars), but fix the size anyway.
- Interfaces are matched by *array index* (`usb_find_interface_driver`) but drivers pass that index to `SET_IDLE`/`GET_DESCRIPTOR` as `wIndex`. That breaks for devices whose `bInterfaceNumber`s aren't 0..n-1 (composite devices do this).
- `usb_calc_bus_time` (`:494-500`): the high-speed branch has ISO and interrupt swapped, and returns **µs** where the caller expects ns, so HS periodic bandwidth is counted roughly 1000× too low. `usb_check_bandwidth` divides by `nPacketNum`, which can be 0 (`:527`).
- `device_uninit` (`:1890`) has no return statement.

## 4. Hub driver (`bus/usb/usb_hub.c`)

### H1. High: hubs with more than 16 ports overflow fixed arrays

`USB_desc_hub` is sized for 16 ports (`:172-173`) and `USB_device_s::psChildren` has 16 entries (`usb.h:155`), but `nMaxChild = nNbrPorts` takes whatever the hub reports, up to 255 (`:321`). Then:

- `portstr[16 + 1]` on the stack is filled up to `nMaxChild` (`:385-387`): a stack overflow.
- `bDeviceRemovable[(i+1)/8]` reads past the 3-byte array.
- `psHub->psChildren[nPort]` is written for every port the interrupt URB reports (`:781,814`), past the array into `psTT`, `nTTPort`, `nHandle` and the next heap object.
- The hub status URB buffer `nBuffer[3]` covers only 23 ports. That limit is correct as a clamp, but nothing ties the port loop to it.

Real 7-port and 10-port hubs are fine. Some multi-TT industrial hubs and every malicious device are not. **Fix:** `if (nNbrPorts > USB_MAXCHILDREN) nNbrPorts = USB_MAXCHILDREN` (and make `USB_MAXCHILDREN` a shared constant), or size everything dynamically.

### H2. High: a failed hub configure leaves a freed hub on the list

`usb_hub_add` (`:506-525`) pushes `psHub` onto `g_psFirstHub` and *then* calls `usb_hub_configure`. On failure it calls `kfree( psHub )` without unlinking it. `usb_hub_irq` or the hub thread later reads `psHub->bNeedsAttention` from freed memory. `usb_hub_configure`'s own failure at `:418-421` also leaves the interrupt packet allocated (and possibly submitted). **Fix:** link only on success, and free the packet and the semaphore on failure.

### H3. High: sleeping with interrupts off in `usb_hub_remove`

`usb_hub_remove` (`:535-569`) does `spinlock_disable(&g_hHubLock)`, then `release_device()`, `LOCK(psHub->hLock)`, `usb_cancel_packet()` (UHCI sync unlink calls `uhci_wait_ms(1)`; OHCI sleeps up to `OHCI_UNLINK_TIMEOUT`, waiting for an SOF interrupt that **can't arrive on this CPU** because interrupts are off), and `delete_semaphore`. It also reads `g_psFirstHub` before taking the lock. **Fix:** unlink from the list under the spinlock, drop it, and then cancel, free and delete outside it.

The hub thread does the same thing in the other direction: `LOCK( psHub->hLock )` while holding `spinlock_cli(&g_hHubLock)` (`:904,924`).

### H4. Medium: other hub problems

- The hub thread is "spawned with a 4 KB stack" (`:1047`), but **`spawn_kernel_thread` ignores `nStackSize`** (`kernel/threads.c:999`). Every kernel thread gets 5 pages (20 KB, `threads.c:620`) with no guard page. So the stack here is 20 KB, not 4 KB. This also means **finding A3 in the SMP/ACPI audit overstates the problem**: the ACPI worker has 20 KB too. It is still worth a look here. The hub thread runs every class driver's `AddDevice` (HID parsing keeps a 4 KB `sLocal` on the stack, D1), and disconnect recurses once per hub tier.
- `usb_hub_irq` (`:256-279`) runs in interrupt context and touches `psHub` with no check that the hub is still alive. That depends on the HCD's cancel being truly synchronous, which OHCI's isn't (O1).
- The topology string loop compares `psPDev->psChildren[nPort]` where it means `[port]` (`:844`), so every level prints the same port.
- High-speed interval: `1 << (bInterval - 1)` is undefined for `bInterval == 0` (`:415`).
- `usb_hub_init` (`:1033`) doesn't NULL-check `pcDriver`.
- On a failed `usb_new_device`, the device is freed with its config still allocated (U5), and the port is disabled and retried once. That's fine.

## 5. Host controller drivers

All three HCDs use **the buffer's virtual address as its DMA address**: `usb-uhci.c:1669-1671`, `usb-ohci.c:1403`, `ehci-q.c:491`, `ehci-sched.c:642` (the `pci_map_single` calls are commented out). That works only for kmalloc memory in the kernel's 1:1 mapped region. Every in-kernel caller uses kmalloc or kernel stacks, so this is OK *except* for M2b below. Note it as a rule: **never hand a user pointer or a non-kmalloc buffer to `submit_packet`.**

### O1. High: OHCI synchronous unlink is a use-after-free

`sohci_unlink_urb` (`usb-ohci.c:797-822`):

```c
urb_priv->wait = create_semaphore( "urb_delete_wait", 0, 0 );
spin_unlock_irqrestore (&usb_ed_lock, flags);
sleep_on_sem( urb_priv->wait, timeout * 1000 );
delete_semaphore( urb_priv->wait );   // urb_priv already freed
urb_priv->wait = -1;                  // write to freed memory
```

The SOF interrupt path `dl_del_urb()` (`:1540-1563`) calls `urb_rm_priv_locked()`, which frees `urb_priv` (`:212`), and *then* wakes the sleeper. So the sleeper always reads and writes freed memory. Also, `wakeup_sem()` before `sleep_on_sem()` is a lost wakeup (that's possible on SMP, or if the frame interrupt fires first), which turns every cancel into a full `OHCI_UNLINK_TIMEOUT` wait. The same pattern is at `:914-930` for `dev->wait`.

**Fix:** copy the sem ID to a local before sleeping and use a counting semaphore (`lock_semaphore`, not `sleep_on_sem`/`wakeup_sem`), so the order doesn't matter. Never touch `urb_priv` after the wait.

### O2. Medium: UHCI

- `process_interrupt` (`usb-uhci.c:2507`) compares with `ECONNRESET`, which should be `-ECONNRESET`. An interrupt URB that a driver async-unlinks from its own completion gets re-armed.
- `:2466` `!desc->hw.td.status & cpu_to_le32(TD_CTRL_IOC)` is `(!status) & IOC`, which is always 0. Add the missing parentheses (`!(... & ...)`).
- The sync unlink (`:1142-1196`) sleeps (`uhci_wait_ms(1)`). That's fine from a thread, but it's called under the hub spinlock (H3).
- Completions run in interrupt context with `urb_list_lock` dropped. Every class driver completion must not sleep. The current ones (`UNLOCK`/`wakeup_sem`) are OK.

### O3. Low: EHCI

`hcd_unlink_urb` (`usb_ehci/hcd.c:991-1110`) follows the Linux 2.5 shape properly (a splice completion and a blocking semaphore). I found nothing memory-unsafe on the unlink and giveback path. As with the others, ISO and periodic scheduling (`ehci-sched.c`) weren't audited line by line.

## 6. Class drivers

### D1. Critical: the HID report descriptor parser has no bounds (`hid.c:506-725`)

The parser runs on bytes the device supplies, on the hub thread's stack:

| Line | Problem |
|------|---------|
| `:590` | `&psHID->asReport[sGlobal.nReportID]`, where the Report ID is 32 bits from the device and the array has 256 entries. This is a heap write anywhere within ±16 GB of `psHID`. |
| `:623` | `apsField[psReport->nNumFields++]`, with no check against 64. |
| `:689` | `sLocal.anUsage[sLocal.nUsageIndex++]`, with no check against 1024 (**stack**). |
| `:700-701` | `for (i = UsageMin; i <= UsageMax; i++) anUsage[idx++] = i;` A range of 0..0xFFFFFFFF writes 16 GB down the kernel stack. |
| `:553-556` | Long item: `pPtr += nSize` (should be `nDataSize`) jumps past the buffer. |
| `:560-579` | 1/2/4-byte item data is read without checking that `nSize` has that many bytes left. |
| `:596-613` | `kmalloc(MEMF_KERNEL)` results aren't checked. `nReportSize * nReportCount` isn't bounded, so `psReport->nSize` overflows. |

In `usbhid_add` (`:761-775`): `psInterface->psEndpoint[0]` is used *before* the `nNumEndpoints == 0` check (the `||` order is wrong), and `asDesc[i]` is read up to `bNumDescriptors` without checking the HID descriptor's `bLength`. The submit failure returns `-EIO` from a `bool` function (`:866`), which is *true*, so the core thinks the device was claimed with `*pPrivate` unset, and `usbhid_remove` then dereferences garbage.

**Fix:** port the bounds checks from Linux's `hid-core.c` (`HID_MAX_USAGES`, `HID_MAX_FIELDS`, report ID ≤ 255, report size ≤ 256 bits × count ≤ `HID_MAX_BUFFER_SIZE`). Move `sLocal` off the stack. Reject the device on any parse error. This one file is the biggest single risk in the stack.

### D2. High: the HID interrupt handler trusts the parsed tables (`hid.c:258-452`)

It runs in interrupt context:
- `int32 nValue[psField->nCount]` (`:314`) is a VLA sized by the device's Report Count, **on the interrupt stack**.
- `psField->anUsage[nValue[j] - nLogMin]` (`:323,388,410`) is only checked against the logical range, not against `nNumUsages`.
- `nCode = nUsage & 0xFFFF` indexes `g_anHidKeyboard[256]`, then `g_anRawKeyTab[]` (`:371-374`, `:397-400`, `:419-422`). The guard `nUsage >= 0 && nUsage >= 255` is always true and should be `nCode < 256`.
- `extract()` reads a `uint64` at `report + (offset/32)*4` with no check against the received length.
- With numbered reports, a zero-length packet makes `nLen--` wrap to 0xFFFFFFFF (`:280`), which skips the length check.
- `1 << (nButton - 1)` with `nButton == 0` is undefined.

**Fix:** clamp `nCount` at parse time and use a fixed per-field `pValues` buffer allocated alongside `pLastValues`. Bounds-check every table index. Check `nLen` before decrementing it.

### D3. Medium: HID buffers and globals

- `anData[8]` (`hid.h:182`) receives up to 32 bytes (`hid.c:824`). It spills into `zName` within the same struct, so it isn't a heap overflow, but the device name gets corrupted, and reports over 8 bytes only parse by accident.
- One global `g_pMouseBuffer[4]` and keyboard ring serve all HID devices. Two mice overwrite each other. Mouse deltas are *replaced*, not added up, between reads, so motion is lost under load (`hid.c:449`, `usbmouse_read:103-105`).
- `usbkeyb_read` (`:192-193`) writes straight to the user pointer while holding a spinlock with interrupts disabled. `sys_read` checks the buffer first (`vfs.c:2496`), so it isn't a kernel-write hole, but it should copy to a local buffer and `memcpy_to_user` after unlocking.
- `struct USB_hid_s` is about 70 KB (256 reports × 64 field pointers) and is allocated with `MEMF_NOBLOCK`, so it fails easily on a fragmented heap.

### M1. High: USB disk unplug (`usb_disk.c:398-405`)

```c
void usbdisk_remove( USB_device_s * psDevice, void *pPrivate )
{
	g_psSCSIBus->remove_host( psDisk->host );
	release_device( psDevice->nHandle );
	atomic_dec( &psDevice->nRefCount );
}
```

Nothing cancels `current_urb` or the CBI `irq_urb`, nothing removes `psDisk` from `us_list`, nothing sets `psDisk->pusb_dev = NULL` (which `usb_stor_Bulk_transport:977` relies on), and nothing frees `psDisk`, its semaphores, the URBs or the SCSI host. An open filesystem or a command in flight keeps calling the transport on a freed `USB_device_s`. Also, every failure path in `usbdisk_add` after `:352` leaks `psDisk`, and `psDisk->host` isn't NULL-checked (`:359-360`).

**Fix:** under `dev_semaphore`, mark the disk gone, cancel both URBs, clear `pusb_dev`, remove the host, unlink from `us_list`, and free once the SCSI layer's last reference is dropped.

### M2. High: the SCSI read/write chunking corrupts data over 64 KB (`bus/scsi/scsi_generic.c`)

`scsi_generic_do_read` (`:103-104,152`), `readv` (`:234-253`), `do_write` (`:293-337`) and `writev` (`:439-471`) split requests into `0xffff`-byte chunks. With 512-byte sectors that is 127 blocks (65 024 bytes), but `nPos`/`pBuffer` advance by 65 535. The next chunk starts at block 127 again, offset by 511 bytes: reads return 511 bytes of stale bounce-buffer data, and writes put the wrong bytes into block 127 onward. Anything over 64 KB in one call hits this, such as `dd bs=1M`, large `readv`s from the block cache, or a filesystem formatter.

**Fix:** chunk size `= (0xffff / nSectorSize) * nSectorSize`. I'd fix this first among the data-integrity items, because it silently corrupts disks.

**M2b (Medium, needs checking):** `scsi_generic_do_write` passes the caller's `pBuffer` straight into the request (`:305`). Reads bounce through `pDataBuffer`. If a raw `write()` on `/dev/disk/usb/...` gets here with the *user* pointer (sys_write only checks it), the HCD hands the controller a user virtual address as a physical one, which writes random physical memory to the disk. Bounce writes through `pDataBuffer` the same way reads do.

### M3. Medium-High: mass storage waits forever

`usb_stor_control_msg` and `usb_stor_bulk_msg` (`transport.c:391,435`) do `LOCK( current_urb->hWait )` with no timeout, holding `current_urb_sem`. A device that NAKs forever (common with cheap card readers) hangs every thread that touches the disk. `usb_stor_CBI_transport` sleeps with `sleep_on_sem(ip_waitq, INFINITE)` (`:828`) *after* the data stage, so an interrupt that arrives during the data stage is lost (`wakeup_sem` doesn't count) and the thread hangs. The CSW residue is ignored (`:1086-1108`), so short reads are reported as complete.

**Fix:** use a timed `lock_semaphore`, async-unlink on timeout and wait for the completion, then run the Bulk-Only reset sequence. Use a counting semaphore for CBI. Honour `bcs.Residue`. Clamp `max_lun` to 15.

### P1. Medium: printer driver (`misc/usb_printer/usbprinter.c`)

- `:739-742`: `else if (nDescLen > USB_PRINTER_NAME_LEN)` should be `>=`. A DESCRIPTION of exactly 128 bytes writes `zName[128] = 0`, which is the low byte of `psDev`, and later dereferences go wrong.
- `usbprinter_read` (`:498-565`) always returns 0. `nReadCount` starts at 0 and is used as the requested size in the `min()` at `:535`, and the read URB is resubmitted with `nBufferLength = 0` (`:522,549`). Bidirectional reads have never worked.
- `usbprinter_write_irq`/`read_irq` (`:575-584`, `:482-491`) return early on error without waking the waiter. The reader sleeps forever, and the writer loops on `continue` until a signal (`:612-626`).
- `bOpen` is tested outside the lock in `open` (`:228`), so two openers can race. Errors mix positive and negative codes.
- Unplug while open is handled well (cleanup is deferred to close). That's the model the libusb node (K4) and `usb_disk` (M1) should copy.

## 7. Userspace: libusb

### Where libusb is used

- **Shipped:** libusb **0.1.12** (released March 2006) in `/system/resources` (`docs/image-contents.md:30,67`; Builder profiles `resources:93`, `gui-base:44`, `workstation:93`). It is built from the Builder recipe `system/apps/utils/Builder/packages/libusb-0.1.12/`, with the Syllable backend `packages/Syllable/libusb-0.1.12/patches/syllable.c` and an autoconf patch. It is **not** in the CMake ports (`cmake/ports/` has only compilers, SSL, cairo, cups and git).
- **Consumers:** SANE backends 1.0.18/1.0.20 (scanners) and libmtp 0.3.0 (both through the 0.1 API). The in-tree code doesn't include `<usb.h>` anywhere. CUPS 1.3.4's USB backend uses the kernel printer node `/dev/printer/usb/N` (`cups-1.3.4.patch:128`), **not** libusb.
- **Abandoned:** there is a `LibUSB-1.0.2` recipe (two copies, `packages/LibUSB-1.0.2/` and `packages/Syllable/LibUSB-1.0.2/`, the latter `status incomplete`). It has no Syllable backend, so it can't have worked.

### L1. Bugs in the current 0.1.12 Syllable backend (`syllable.c`)

- `req.nTimeout = timeout * 100` (`:126,225`): libusb timeouts are in ms and `bigtime_t` is µs, so every timeout is 10× too short. It should be `* 1000`, and `0` should map to infinite.
- `do_io_request` returns `size`, not the actual transfer length (`:131-132`). Together with K3, callers process stale kernel heap as data. `usb_interrupt_read`'s loop always ends after one call.
- `usb_claim_interface`/`release_interface` are no-ops (`:81-95`), so nothing stops two processes, or a process and a kernel driver, from using the same interface.
- `usb_clear_halt` relies on the kernel ioctl, which clears ep0 (K5).
- `usb_os_find_devices` (`:297-321`) leaks `dev` when `open()` fails, and on the ioctl failure path leaks `dfd`, `bfd` and the list so far, and prints the uninitialised `buf` with `%s`.

The quick fix for 0.1.12 is three one-line patches: `*1000`, return the actual length once the kernel reports it (K3), and the `find_devices` cleanup.

### How to upgrade

The current releases are **libusb 1.0.30** and **libusb-compat-0.1 v0.1.9** (from their GitHub tags, checked today). Upgrading means writing a Syllable backend for libusb 1.x, then building compat-0.1 on top so SANE and libmtp keep working without changes. Plan:

1. **Fix the kernel ioctl layer first** (K1–K5). libusb-1.x's backend contract assumes real actual lengths, a status per transfer, interface claiming and working cancel.
2. **Extend `syllable/libusb.h`** (and bump an ABI version ioctl) with:
   - `IOCNR_CLAIM_INTERFACE`/`RELEASE_INTERFACE` (refuse if a kernel driver owns it, with an optional detach)
   - `nActual` and `nStatus` out-fields on `usb_io_request`
   - `IOCNR_GET_CONFIG_DESC` returning `pRawDescs[n]` (libusb 1.x wants raw descriptors rather than control-message fetches)
   - `IOCNR_GET_ACTIVE_CONFIG` and `IOCNR_RESET_DEVICE` (wrapping `usb_reset_device`)
   - optionally an async submit/reap pair (`IOCNR_SUBMIT_URB`/`IOCNR_REAP_URB` with a waitable fd) like Linux usbfs
   - **one node per device**, not per interface, because libusb 1.x opens a device and then claims interfaces.
3. **Write `libusb/os/syllable_usb.c`**, implementing `struct usbi_os_backend`: `get_device_list` (walk `/dev/usb/<bus>/`), `open`/`close`, `get_active_config_descriptor`, `get_config_descriptor`, `set_configuration`, `claim/release_interface`, `set_interface_altsetting`, `clear_halt`, `reset_device`, `submit_transfer`/`cancel_transfer`/`handle_transfer_completion`. The Haiku backend (`libusb/os/haiku_*.cpp`) is the closest model. It uses blocking calls on a worker thread per transfer and signals completion through libusb's internal event pipe, which works with the current synchronous ioctls (no async kernel API needed for a first version). Isochronous transfers can return `LIBUSB_ERROR_NOT_SUPPORTED` at first.
4. **Wire up the build:** add a `*-syllable*` case to `configure.ac` (`backend="syllable"`, `threads=posix`) and a `OS_SYLLABLE` conditional in `libusb/Makefile.am`. libusb 1.0.30 needs C11 atomics (`stdatomic.h`, GCC ≥ 4.9), so this builds only with the upgraded cross GCC (`branches/step1-gcc-upgrade.md`), not 4.1.2. It also uses `pthread_condattr_setclock` and `clock_gettime(CLOCK_MONOTONIC)`. Check that the Syllable glibc 2.7 port has both, or add a fallback in `os/threads_posix.c`.
5. **Build libusb-compat-0.1 v0.1.9** against the new libusb-1.0, install it as `libusb-0.1.so.4` with `usb.h`, and retire the 0.1.12 package and the `syllable.c` patch.
6. **Add both as CMake ports** (`cmake/ports/45-libusb.cmake`), following the `40-cups.cmake` `ExternalProject_Add` pattern (pinned GitHub tag tarball with SHA256, staging sysroot, cross toolchain env), so they come out of the main build instead of Builder.
7. **Test:** run `examples/listdevs`, `testlibusb` and `xusb` from the libusb tree under QEMU. Pyro has no xHCI driver, so use EHCI with companion UHCIs (`-device ich9-usb-ehci1` plus `ich9-usb-uhci*`) and attach `usb-tablet` and `usb-storage` devices. Then run `scanimage -L` to check SANE.

Expected effort: about 1–2 days for the kernel ioctl changes (on top of fixing K1–K5), about 2–3 days for the backend, and half a day for the build glue.

## 8. Appserver USB input drivers

- `usbkeyboard/keyboard.cpp:125-130` reads one byte at a time with a 10 ms `snooze` between reads, even though `read()` already blocks in the kernel. That's up to 10 ms of extra key latency per byte, and typing gets dropped behind bursts. Remove the `snooze` and read into a buffer.
- `usbmouse/usbmouse.cpp:174-177`: on a read error it `continue`s with no delay, which pins a CPU at 100% if the kernel node starts failing (for example after D-series errors). Back off or exit.
- The mouse only reports 3 buttons and vertical scroll. Horizontal scroll and buttons 4/5 are dropped because the kernel's 4-byte format can't carry them (D3). That's a feature gap, not a bug.
- Both drivers depend on the single global HID buffers in the kernel (D3).

No memory-safety problems in the userspace drivers themselves.

## 9. Fix order

1. **D1 + D2 (HID parser and IRQ bounds).** Any USB keyboard or mouse with an unusual descriptor, or any malicious stick, corrupts the kernel on plug-in. This is the most exposed code.
2. **M2 (SCSI 64 KB chunking).** A one-line fix for silent disk corruption on every USB stick. Do it alongside M2b (bounce writes).
3. **K1–K4 (libusb ioctl).** User-triggerable kernel use-after-free, OOB read and heap disclosure. If a quick stopgap is needed, make `/dev/usb/*` root-only until these are fixed.
4. **O1 (OHCI unlink use-after-free)** and **U1 (blocked-submit use-after-free).** Both are small, local swaps.
5. **H1–H3 (hub port clamp, failure unlink, sleeping under the spinlock)** and **U2 (`g_hUSBLock` around probing).** Turn the probe locks into semaphores.
6. **M1 + M3 (USB disk unplug and timeouts).** Unplugging a mounted stick should not crash the kernel.
7. **U3 + U4 + U5 (descriptor parsing and lifetime leaks).**
8. **P1 (printer)**, **O2 (UHCI typos)**, **section 8 (appserver)**.
9. **libusb upgrade** (section 7, steps 2–7), once the kernel side is sound and the GCC upgrade has landed.

**Verification:** QEMU with `-device ich9-usb-ehci1,id=ehci -device ich9-usb-uhci1,masterbus=ehci.0 -device usb-kbd -device usb-mouse -device usb-storage,drive=stick` covers EHCI, UHCI, HID and mass storage. Use `-device pci-ohci` for OHCI. For the descriptor bugs (U3, U4, H1, D1, D2), a Linux `dummy_hcd` + `raw-gadget` (or a Facedancer) can present hostile descriptors, which turns this audit into regression tests. The `syzkaller` USB descriptor corpus is a ready-made input set.

## 10. Correction to the SMP/ACPI audit

Finding A3 in `docs/smp-acpi-audit-2026-11-10.md` says the ACPI worker runs on "a 4 KB kernel stack". `spawn_kernel_thread()` (`kernel/kernel/threads.c:999`) ignores its `nStackSize` argument, and every thread's kernel stack is `PAGE_SIZE * 5` = 20 KB (`threads.c:620`). The real problem is 20 KB with **no guard page**, so an overflow still silently corrupts the neighbouring heap object. That's less urgent than the audit said, and the fix (a dedicated worker with a known stack, or a guard page) is unchanged. Separately, `spawn_kernel_thread` should either honour `nStackSize` or drop the parameter, since its callers believe they control it.
